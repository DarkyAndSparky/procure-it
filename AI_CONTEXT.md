# Procure-IT — контекст для ассистента

Вставьте этот файл первым сообщением в новый чат (плюс актуальный zip
проекта) — дальше можно сразу работать, не пересказывая по новой.

## Что это
Procure-IT — внутренняя система учёта закупок ИТ-отдела. Node.js/Express
+ SQLite (`sql.js`) + vanilla JS фронтенд (без сборщика, обычные
`<script src>`). Разрабатывается вдвоём (я + разработчик) для 4-5
пользователей компании с несколькими удалёнными филиалами.

## Главное правило квартала
> Не переписывать то, что уже работает, пока проблема не доказана.

Никакого React/PostgreSQL/микросервисов/тяжёлых зависимостей без
конкретной, доказанной необходимости — см. `ROADMAP_Q4.md` §18. Ценность
квартала — надёжность → прозрачность → удобство → аналитика, не новые
технологии.

## Обязательный процесс на КАЖДОЕ изменение кода
После любой правки в `src/`, `public/js/` или `public/*.html` — **в том
же заходе**, не откладывая:
1. Обновить `CHANGELOG.md` — новая запись с описанием, что и почему
   починено/добавлено (см. существующие записи как образец стиля —
   подробно, с формулировкой найденного бага и как проверено).
2. Бампнуть версию: `npm run bump` (считает `YYwWW-STAGENN` сам — не
   вычислять вручную). Есть `-- --dry-run`, чтобы посмотреть заранее.
3. `npm run version:sync` вызывается автоматически внутри `bump`, вручную
   не нужно.
4. Архив, который отдаётся пользователю, называть с номером билда в
   имени файла — `procure-it-dev-<версия>.zip` (например
   `procure-it-dev-26w39-b07.zip`), не общим именем без версии. Так
   видно из имени файла, что внутри, не открывая архив и не сверяя
   `package.json`.
5. Перед сборкой архива — `npm test` (unit, `node --test`). Не
   собирать и не отдавать архив, если тесты не прогнаны в этом же
   заходе или прогнаны, но падают. E2E (`npm run test:e2e`) сюда не
   входит — не прогнать без сети до Playwright CDN в этой среде, но
   именно это стоит явно проговаривать, а не молчать.
Это не формальность — есть pre-commit хук, который напоминает, если
`CHANGELOG.md` не тронут вместе с кодом.

## Ограничения этой рабочей среды (важно проговаривать честно)
- **Нет браузера** — фронтенд-правки проверяются только чтением кода
  (сверка полей между бэкендом и фронтом, ручная трассировка потока
  данных), не живым рендерингом. Явно писать в CHANGELOG, что именно не
  проверено вживую.
- **Нет сети до Playwright CDN** — E2E не прогнать.
- **Нет `.git`** в архиве — нельзя проверить git history на утечку
  секретов.
- В архиве не бывает файла БД (`data/zakupki.db`) — если нужно
  прогнать что-то на реальных данных, БД создаётся с нуля (заводит
  админа с одноразовым паролем в консоли).

## Где что лежит
- `ROADMAP_Q4.md` — план квартала по неделям/секциям, там же §17.5 —
  зафиксированные находки от сравнения с похожими open-source проектами
  (backlog, не в приоритете) и §18 — главное правило.
- `CHANGELOG.md` — единственный источник истины по истории изменений,
  парсится `src/changelog.js` для страницы «О системе».
- `docs/index.html` — подробная техническая документация (дерево
  проекта, API-эндпоинты, форматы) — держать в синхроне с реальным
  кодом при структурных изменениях (проверено на практике: минимум
  дважды документация отставала от кода — CSV-кнопка, которой не было;
  скрипты, которых не было в дереве).
- `CONTRIBUTING.md` — git-flow (`dev`→`main` через `tools/release/`),
  формат коммитов, подробности версионирования.
- `scripts/` — утилиты, входят в релиз (нужны Dockerfile/install-скриптам).

## Стиль работы, который сложился
- Находить реальные баги через прослеживание кода построчно (не
  предполагать «наверное работает»), явно указывать, чем подтверждено —
  живым прогоном/тестом, либо только чтением (и тогда что именно не
  проверено).
- Мелкие фиксы — сразу молча чинить, не спрашивать разрешения на
  каждую мелочь.
- Спорные/архитектурные решения (наращивать функциональность,
  переносить фичи из других проектов) — сверять с §18 и явно
  проговаривать trade-off, не делать по умолчанию.
- Сравнение с другими проектами — только как источник идей на будущее,
  не как повод копировать «раз у них есть».
