# Changelog

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.0.0/).
Версии — по внутренней схеме `YYwWWr-bNN` (год-неделя, релиз/билд).

Этот файл — единственный источник истины для истории изменений: раздел
«Последние изменения» на странице «О системе» приложения парсит именно его
(`src/changelog.js`), отдельного дублирующего списка в коде нет.

**Каждый значимый коммит должен добавлять сюда запись.** Pre-commit хук
(`scripts/hooks/pre-commit`, ставится через `npm install` → `prepare`)
напоминает об этом, если меняются файлы в `src/`, `public/js/` или
`public/*.html`, а `CHANGELOG.md` в этом же коммите не тронут.

## [26w34-b07] — 2026-08-24

Аудит перед мерджем dev→main, инициированный вручную (не автоматическим
циклом) — два открытых пункта из предыдущего раунда безопасности закрыты
до конца, плюс первый e2e-слой поверх существующих unit/интеграционных
тестов.

### Добавлено
- **E2E-тесты на Playwright** (`e2e/`, `playwright.config.js`) — первый
  слой тестов, гоняющих настоящий браузер против настоящего сервера, а не
  только HTTP-запросы напрямую. Сеттап заводит admin/operator/viewer
  через API один раз на прогон (`e2e/auth.setup.js`) и переиспользует
  `storageState` (токен в localStorage — приложение не использует куки
  для сессии) вместо повторного прохождения формы логина в каждом тесте.
  Покрытие: логин-форма и гостевой режим (`auth.spec.js`), организации —
  создание/дубликаты/редактирование/удаление (`orgs.spec.js`), полный
  цикл заявки — создание с проверкой реального расчёта наценки, сохранение,
  поиск в реестре, смена статуса, редактирование с пересчётом суммы,
  удаление (`request-lifecycle.spec.js`), ролевые границы viewer/
  operator/admin — и то, что скрыто в UI, и то, что сервер реально
  отклоняет 403/400 при прямых запросах в обход UI (`permissions.spec.js`).
  Требует `npx playwright install chromium` перед первым запуском —
  браузер не входит в `npm install`. Запуск: `npm run test:e2e`.
- `src/config.js` — `PROCURE_DATA_DIR` (опциональная переменная
  окружения) — позволяет e2e-прогону поднять сервер на изолированной
  временной директории данных вместо `data/` репозитория. Без неё e2e
  реально писал бы в рабочую БД разработчика при локальном запуске. Не
  задана — поведение не меняется ни на бит.

### Исправлено
- **Stored XSS через поле «ед. изм.» позиции** — `public/js/registry.js`,
  `buildDetailHtml()`. Единственное место в детальном виде заявки, где
  значение из БД вставлялось в `innerHTML` без `esc()` (все соседние поля
  — `name`, `comment`, `address` и т.д. — были экранированы, `unit` —
  нет). Поле — свободный `<input type="text">` в форме заявки, доступный
  любому operator/admin. Эксплуатация: вписать в «ед.» HTML с
  обработчиком события (`<img src=x onerror=...>` — инлайн-скрипты и
  обработчики разрешены текущим CSP, `scriptSrc`/`scriptSrcAttr`
  содержат `'unsafe-inline'` — так что сама по себе CSP это не блокирует),
  сохранить заявку — код выполнится в браузере ЛЮБОГО пользователя,
  включая admin, который развернёт эту заявку в реестре. Токен сессии —
  в `localStorage`, не в httpOnly-куке, так что это прямая эскалация
  привилегий (кража admin-токена оператором). Найдено при ручном аудите
  перед мерджем в main, не автотестами.
- **`total`/`totalPurchase` заявки принимались от клиента как есть** —
  предыдущий раунд аудита (`26w34-b01`) добавил только сверку-с-логированием (`logTotalsMismatch`), сознательно отложив
  решение «что делать» до отдельного разговора. Решение принято: сервер
  теперь сам считает обе суммы из `positions` той же формулой
  (`calcRowPricing` — общий модуль для браузера и Node, `public/js/
  pricing-core.js`) и полностью игнорирует значения этих двух полей в
  теле запроса — подделать сумму заявки через прямой API-запрос (в обход
  формы, например через devtools) больше нельзя. Суммы ВНУТРИ каждой
  позиции (`purchaseSum`/`sellPerUnit`/`sellSum`) по-прежнему приходят от
  клиента без изменений — это то же самое, что видел пользователь в
  форме перед сохранением; пересчёт и их тоже — отдельная, более крупная
  правка, не обязательная для закрытия именно этой дыры (итоговые суммы
  заявки — то, что уходит в спецификацию/счёт/Bitrix и статистику по
  организациям). Расхождение с присланным клиентом всё ещё логируется
  (`console.warn`) — полезный сигнал о рассинхронившейся версии
  фронтенда, просто больше не единственная защита. Проверено вживую:
  POST с `total: 1` на позиции суммой 105000 ₽ — сервер сохранил и
  вернул `total: 105000`, не `1`. Регресс на существующих 58 unit-тестах
  — все проходят без изменений (`calcRowPricing` не менялся, только
  точка, где используется его результат).

## [26w34-b02] — 2026-08-20

### Исправлено
- **`.bat`-скрипты не запускались на реальной Windows** — в b01 весь
  видимый текст в `install.bat`/`start.bat`/`test.bat` был переведён на

  external command`. Все три `.bat`-файла переписаны в чистый ASCII
  (включая комментарии, не только видимый текст). `.sh`-версии кириллицу
  сохранили — той же проблемы там нет: bash токенизирует байтовые потоки
  равномерно, шелл-метасимволы все в ASCII, конфликтовать с
  многобайтовыми UTF-8-последовательностями кириллицы им негде

- `test.sh`/`test.bat` — отдельный запускатор тестов, не завязан на `start`/`install`

### Изменено
- `playwright` перенесён из `dependencies` в `devDependencies` — нигде не используется в коде/тестах, реально пропускается `npm ci --omit=dev` (в т.ч. в Dockerfile), заметно снижая вес прод-инсталла

### Исправлено
- `start.bat` открывал браузер по фиксированному таймеру параллельно со стартом сервера (гонка, могла открыть браузер раньше готовности сервера) — перенесено в колбэк `.listen()` в `server.js`, управляется `PROCURE_AUTO_OPEN=1`
- `start.bat` требовал двух запусков после свежей установки — `npm install` вызывался без `call`, что в Windows batch обрывало выполнение родительского скрипта сразу после установки зависимостей. Исправлено (`call npm install` в `install.bat`), заодно добавлены `cd /d "%~dp0"` и CRLF-окончания строк во всех `.bat`-файлах для устойчивости
- `install.sh`/`install.bat` не проверяли минимальную версию Node.js и не отличали сбой `npm install` (нет интернета, заблокирован registry) от успеха — оба добавлены, с понятными сообщениями об ошибке
- Проверка «нужно ли переустанавливать зависимости» была завязана на существование одного пакета (`node_modules/express`) — теперь сравнивается время изменения `package-lock.json` против `node_modules` (в `.bat` — через `node -e`, не через batch-даты, которые зависят от региональных настроек Windows)
- `test.sh`/`test.bat` дублировали часть проверок install-скриптов — переписаны на вызов `install.*` с флагом `--from-start`
- Все `.bat`-скрипты (`install.bat`/`start.bat`/`test.bat`) переведены на русский — были на английском, тогда как `.sh`-версии на русском; несогласованность для пользователей с русской локалью Windows
- Утечка секретов вебхуков (Bitrix24, статус) в скачиваемый JSON-бэкап — исключены из выгрузки так же, как пароль сетевой папки
- Command injection через название заявки при открытии папки заявки и через логин/пароль сетевой папки на Windows — переведено на `execFile`/массив аргументов без участия shell
- Общая PBKDF2-соль на всех пользователей заменена на соль-на-пользователя, с автоматической миграцией существующих записей при следующем входе
- Восстановление из бэкапа не проверяло роль пользователя по белому списку `['viewer','operator','admin']`, в отличие от обычного создания/редактирования пользователя

- `GET /api/backup` (JSON) добавлен под тот же `strictLimiter`, что и `GET /api/backup/db`

- Автотесты на аутентификацию (`test/auth.test.js`) — соль-на-пользователя, миграция легаси-форматов пароля (общая PBKDF2-соль и самый старый голый SHA-256) при успешном входе, отказ на неверном пароле без побочной миграции
- Сравнение секретов через обычное `===` заменено на timing-safe (`crypto.timingSafeEqual`) — конкретно `password === LEGACY_PASSWORD` в `findUserByCredentials` (сравнение сырого секрета, а не хэша — реальный, не теоретический риск тайминг-атаки), заодно и сравнения хэшей паролей для единообразия; покрыто автотестами (`timingSafeStringEqual` — совпадение/несовпадение/разная длина/пустые значения)
- `Dockerfile` — сборка образа падала на первом же `RUN npm ci`: `package.json` копировался раньше `scripts/`, а `prepare`-хук (`node scripts/install-hooks.js`) запускается именно при `npm ci`.
