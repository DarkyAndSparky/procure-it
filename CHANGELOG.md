`public/*.html`, а `CHANGELOG.md` в этом же коммите не тронут.

## [26w36-b12] — 2026-09-10

### Исправлено (найдено вживую на машине пользователя — два бага в одном инциденте)
- **Смена временного пароля падала с `EPERM: operation not permitted, rename '...zakupki.db.tmp-N' -> '...zakupki.db'`** прямо в UI — воспроизведено на реальной Windows (путь на скриншоте — `Desktop\...`, что указывает на OneDrive Known Folder Move: OneDrive/антивирус кратковременно блокируют файл сразу после записи, `rename()` на Windows, в отличие от POSIX, требует, чтобы целевой файл в этот момент был не занят). `saveDb()` (`src/db/connection.js`) теперь ретраит `rename()` до 8 раз с короткой синхронной паузой (`Atomics.wait`) при `EPERM`/`EBUSY` — воспроизведено и подтверждено: 2 неудачи подряд → успех на 3-й попытке; постоянная блокировка → честный `throw` после исчерпания попыток (~560мс), не зависание
- **Повторная попытка смены пароля после первого сбоя требовала «Укажите текущий пароль»**, хотя пользователь всё ещё видел экран «временный пароль, смените». Корень — `run()` (`src/db/connection.js`) применяет `UPDATE` к in-memory БД sql.js мгновенно, а `saveDb()` (запись на диск) вызывается следом и может упасть отдельно — при сбое **только на этом шаге** память и диск расходились: сервер «думал» (по памяти), что `must_change_password` уже сброшен, хотя на диске всё осталось по-старому. `src/routes/auth.js` теперь читает старые значения до `UPDATE` и явно откатывает их при неудаче сохранения — подтверждено integration-тестом: после сбойной попытки `mustChangePassword` остаётся `true`, повторная попытка (когда диск снова доступен) проходит без требования currentPassword
- **`run()` глотала ошибку записи на диск молча**, возвращая `false` без различения причины (SQL constraint violation vs файловый сбой) — из 72 мест в проекте, вызывающих `run()`, только 2 проверяли возвращаемое значение. `run()` теперь различает источник: SQL-ошибки (как `UNIQUE`) по-прежнему тихо возвращают `false` — это осознанно нужно двум местам в `requests.js` для сообщения «номер спецификации уже занят» — а ошибка именно `saveDb()` теперь пробрасывается наружу как исключение, попадая в глобальный error-handler вместо тихой потери данных с `res.json({ok:true})`
- **Глобальный error-handler (`server.js`) отдавал `err.message` клиенту как есть** для любого непойманного исключения — это и было прямой причиной утечки полного пути к файлам БД в UI на скриншоте. Теперь для непредвиденных (500) ошибок отдаётся общее сообщение; специально написанные для пользователя ошибки (`res.status(4xx).json({error:'...'})` внутри route) не затронуты — они возвращаются раньше, минуя этот handler
- **17 мест по всему проекту** с тем же паттерном локального `catch(e) { res.status(...).json({error: e.message}) }`, обходящим глобальный error-handler — при развороте изменений `run()`/`saveDb()` (throw вместо тихого `false`) часть из них (`backup.js`, `settings.js`, `files.js` — все три реально используют `run()`/`saveDb()`) стала бы новым путём той же утечки технических деталей сервера. Исправлены все места, где это утечка непредвиденных ошибок (в т.ч. 4 избыточных дублирующих явных `saveDb()` после уже-сохраняющей `run()` — убраны). Оставлены как есть 2 места, где `e.message` осознанно полезен пользователю как часть диагностики (`/settings/smtp-test`, `/test-folder` — оба администратор сам запускает, чтобы проверить настройку внешнего сервиса, и текст ошибки соединения там — не «утечка», а суть ответа)
- Всё проверено integration-тестом, реально воспроизводящим оба бага со скриншотов через симуляцию `EPERM` в реальном HTTP round-trip (не изолированный юнит-тест) — все 6 проверок зелёные, включая финальное подтверждение, что пароль реально сохраняется на диск (повторный логин с новым паролем), не только в памяти процесса. 58/58 существующих юнит-тестов не задеты

## [26w36-b04] — 2026-09-06

### Исправлено
- **Поиск в реестре заявок не находил кириллические совпадения при разном регистре** (`GET /api/requests?q=...`) — например, поиск «закуп» не находил сохранённое «Закуп». Причина: фронтенд приводит поисковую строку к нижнему регистру через `String.prototype.toLowerCase()` (корректно ICU-aware, работает для любого языка), а поиск шёл через SQL `LIKE`, чья встроенная в SQLite регистронезависимость касается **только ASCII** — кириллица в `LIKE` сравнивается регистрозависимо буквально. Найдено реальным прогоном e2e (`request-lifecycle.spec.js` — заявка с кириллическим именем не находилась в реестре сразу после создания и сохранения). Воспроизведено и подтверждено вручную через API до и после фикса. Исправлено переносом текстового поиска (`q`) из SQL `LIKE` в JS-фильтрацию (`.toLowerCase().includes()`) после остальных SQL-фильтров (org/month/status/supplier/counterparty остаются в SQL — это точные ASCII-совпадения, их не касается). Пагинация теперь считается после JS-фильтра, а не через отдельный `COUNT(*)`-запрос

## [26w36-b03] — 2026-09-06

### Исправлено (регрессия из `26w36-b01`, найдена реальным прогоном e2e)
- **`script-src-attr 'unsafe-inline'` возвращён в CSP.** В `26w36-b01` это значение убрали, посчитав, что все inline-обработчики (`onclick=`/`onchange=`/`onkeydown=`) вынесены в `addEventListener`. На деле конвертация коснулась только СТАТИЧНОЙ разметки (`public/zakupki.html`, `reset-password.html`) — но заметная часть интерфейса рендерится через `innerHTML` во время выполнения (модалка логина, строки реестра, строки позиций заявки, списки организаций/пользователей — см. `auth.js`, `registry.js`, `positions.js`, `users.js`, `config.js`, `helpers.js`), и там inline-обработчики как были, так и остались в шаблонных строках. Без `unsafe-inline` в `scriptSrcAttr` браузер молча отбрасывает такие обработчики — без ошибки в консоли, без исключения — снаружи это выглядит как «кнопка не реагирует». Реальный прогон e2e (после того как в `26w36-b02` наконец заработали `.bat`-скрипты) поймал это: 8 из 23 тестов упали, включая базовый вход в систему (модалка логина не закрывалась после клика «Войти») и удаление строк/организаций. Все 8 падений трассируются к этой ОДНОЙ причине
- Полноценный фикс (перевод оставшихся ~43 динамических обработчиков на event delegation) требует реального браузера для проверки на каждом шаге — не сделан в этой сессии. `scriptSrcAttr` намеренно оставлен с `unsafe-inline` до тех пор
