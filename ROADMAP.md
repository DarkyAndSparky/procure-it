## 🔴 Приоритет — безопасность и бэкапы (по итогам аудита)

- [x] **Секреты вебхуков утекают в JSON-бэкап** — `GET /api/backup` теперь
      исключает `bitrixWebhook` и `statusWebhook` из `settings` так же, как
      `networkPass` (единый список `SECRET_SETTINGS`). Проверено — бэкап с
      настроенными вебхуками их не содержит.
- [x] **Command injection через `exec()` при открытии папки заявки** —
      `openFolder()` переведён на `execFile`/массив аргументов вместо
      строковой shell-команды; путь передаётся ОС напрямую, без участия
      shell. Проверено на реальном payload в названии заявки
      (`Заявка $(touch /tmp/marker)`) — маркер-файл не создаётся, полезная
      нагрузка попадает в имя папки как обычный текст.
- [x] **Тот же паттерн в `mountSmbIfNeeded`** — переведён на
      `execFileSync('net', [...])` вместо строковой команды в `execSync`.
- [x] **Общая PBKDF2-соль на всех пользователей** — соль теперь
      генерируется на каждого пользователя отдельно (`users.salt`,
      `crypto.randomBytes(16)`) и хранится рядом с хэшем. Записи со старой
      общей солью (и самые старые — на голом SHA-256) автоматически
      доигрываются до нового формата при следующем успешном входе, без
      принудительного сброса пароля всем сразу. Проверено: логин легаси-
      записью мигрирует соль, новый пароль/логин работают.
- [x] **Restore не валидирует роль пользователя** — `POST /api/restore`
      теперь фильтрует `role` по тому же белому списку
      `['viewer','operator','admin']`, что и `POST/PUT /api/users`.
      Проверено: восстановление бэкапа с внедрённым пользователем
      `role: 'superadmin'` — такой пользователь не создаётся, остальные
      данные восстанавливаются штатно.
- [x] **`requireSafeId` не на всех роутах с файлами** — добавлен на GET
      `/requests/:id/signed-spec`/`invoice-file` (см. 🟡 ниже — закрыто
      вместе со следующим приоритетом, без отдельного захода).
- [ ] **`.env` закоммичен в git, несмотря на `.gitignore`** — файл уже
      отслеживается; `git rm --cached .env` — выполняется вручную в
      терминале (не входит в поставляемый архив с правками кода).

## 🟡 Следующий приоритет — доведение аудита

- [x] **Нет автотестов на auth-логику, хотя в этом цикле она переписана** —
      миграция паролей на соль-на-пользователя (см. 🔴 выше) проверялась
      только вручную через curl; такой код — ровно то, что легко тихо
      сломать следующей правкой, не заметив локально (конкретный
      пользователь просто перестаёт входить). Добавлен `test/auth.test.js`
      (7 тестов): разные соли на разные хэши, вход по текущему формату,
      миграция обеих легаси-схем при успешном входе, отказ без побочной
      миграции на неверном пароле, несуществующий пользователь. Изолирован
      от реальной `data/zakupki.db` — in-memory sql.js, как в
      `schema.test.js`.

- [x] **Сервер не пересчитывает сумму/цены заявки** — `POST`/`PUT
      /api/requests` теперь пересчитывает ожидаемые `totalPurchase`/`total`
      из `positions` той же формулой, что и клиент (`pricing-core.js`,
      переиспользован как есть — изоморфный модуль), и логирует
      расхождение сверх допуска на округление. Не блокирует сохранение —
      сознательно, чтобы не ломать существующий флоу; это наблюдаемость,
      не enforcement. Проверено: заявка с намеренно неверной суммой даёт
      запись в логе, с верной — нет.
- [x] **`GET /api/system-info` доступен operator, не только admin** —
      оба роута (`/system-info`, `/system-info/outdated`) переведены на
      `adminOnly` — приведено в соответствие с тем, что в UI страница «О
      системе» и так видна только admin (`data-role-min="admin"`).
      Проверено: operator получает 403, admin — 200, остальные
      operator-функции не затронуты.
- [x] **`Date.now()` как id организаций/заявок** — заменено на
      `crypto.randomUUID()` во всех трёх местах генерации id (создание
      организации, bulk-импорт, создание заявки). Проверено: раскладка
      файлов не завязана на формат id (сопоставление папки и заявки идёт
      через маркер-файл с id внутри, не через имя папки), `SAFE_ID` regex
      в restore пропускает UUID.
- [x] **Несимметричный rate limit на бэкапах** — `GET /api/backup` (JSON)
      теперь тоже под `strictLimiter`, как и `GET /api/backup/db`.
- [x] **`requireSafeId` не на всех роутах с файлами** — добавлен на GET
      `/requests/:id/signed-spec` и `/requests/:id/invoice-file`
      (закрыто заодно с этим циклом, было отложено с прошлого).

## ✅ Инфраструктура сборки — по запросу

- [x] **`install.sh`/`install.bat` — установка без запуска сервера** —
      выделены из `start.sh`/`start.bat` (та же логика: проверка Node.js,
      `npm install`, подготовка `data/`+`logs/`), теперь можно подготовить
      окружение отдельным шагом (systemd-юнит, шаг CI-сборки и т.п.) без
      побочного запуска сервера. `start.sh`/`start.bat` теперь просто
      вызывают `install.sh --from-start`/`install.bat --from-start`
      (без дублирования баннера/логики) и продолжают запуском сервера —
      поведение по умолчанию не изменилось.
- [x] **`test.sh`/`test.bat` — отдельный запускатор тестов** — обёртка над
      `npm test` с проверкой Node.js/зависимостей, не завязана на
      `start`/`install`. Тесты и так не запакованы в Docker-образ
      (`Dockerfile` не копирует `test/`), но теперь это явно и для
      локального dev-сценария тоже, не только для контейнера.
- [x] **`playwright` был в `dependencies`, хотя нигде не используется** —
      найдено попутно: пакет не встречается ни в `src/`, ни в `test/`, ни в
      Dockerfile/CI — только декоративно в списке технологий на странице
      «О системе» (`config.js`, секция «Dev-зависимости» в бэкенде уже
      была готова к этому разделению, просто `package.json` не содержал
      `devDependencies`). Перенесён в `devDependencies` — теперь реально
      пропускается `npm ci --omit=dev` (как в Dockerfile), экономя
      значительный вес и в проде, и при `npm ci` в CI. Проверено:
      `npm ci --omit=dev` не ставит `playwright`, `npm test` на таком
      инсталле всё равно проходит все 25 тестов (значит, тестам он и не
      был нужен).
- [x] **`.dockerignore`** — добавлены `install.*`/`test.*` и явное правило
      на `test/` (Dockerfile и так не копирует эти пути через явный
      whitelist `COPY`, но правило описывает намерение явно — на случай,
      если `COPY` когда-нибудь заменят на `COPY . .`).
- [x] **`start.bat` открывал браузер по таймеру, не по факту готовности
      сервера** — гонка: `timeout /t 3` работал параллельно со стартом
      сервера, и если старт (генерация сертификата, инициализация БД на
      первом запуске) занимал дольше 3с, браузер открывался раньше и
      показывал ошибку подключения. Открытие браузера перенесено в сам
      `server.js` — вызывается из колбэка `.listen()`, единственного
      места, где сервер объективно уже готов принимать соединения.
      Управляется `PROCURE_AUTO_OPEN=1` (выставляет только `start.bat`
      перед запуском) — обычный `node server.js` (Docker/systemd/headless)
      это не затрагивает. Проверено: сервер с `PROCURE_AUTO_OPEN=1`
      стартует и логирует штатно (в контейнере sandbox нет `xdg-open`,
      попытка тихо игнорируется через try/catch, сервер не падает); лог
      запуска идентичен обычному запуску без переменной.
- [x] **`start.bat` требовал двух запусков после свежей установки** —
      причина: исходный `start.bat` вызывал `npm install` (а это
      `npm.cmd`, то есть тоже batch-скрипт) БЕЗ `call`. В Windows batch
      вызов другого `.bat`/`.cmd`-файла без `call` не возвращает
      управление обратно — весь родительский скрипт завершается сразу
      после того, как отработает вызванный. На первом запуске (нет
      `node_modules`) это обрывало `start.bat` сразу после установки
      зависимостей, до строки с `node server.js`; на втором запуске
      (зависимости уже есть) ветка с `npm install` не выполнялась вообще,
      и скрипт беспрепятственно доходил до старта сервера — отсюда
      ощущение «нужно запускать дважды». `install.bat`/`test.bat` (этот
      цикл) сразу писались с `call npm install`/`call npm test` — этой
      ошибки в них не было, но заодно докручено: `cd /d "%~dp0"` в начале
      всех трёх `.bat`-файлов (устойчивость к запуску не из собственной
      директории — ярлык с другим «Рабочая папка», Планировщик заданий) и
      CRLF-окончания строк во всех трёх (Windows `cmd.exe` менее
      предсказуемо разбирает многострочные `if...else (...)` блоки с
      LF-окончаниями).
- [x] **Ревизия install/start/test-скриптов под русскую локаль** —
      несколько находок разом:
      · проверка минимальной версии Node.js (`engines.node` из
      `package.json`) была вообще не реализована — старый Node просто
      падал бы с невнятной ошибкой при первом же `require`/синтаксисе,
      которого не знает. Добавлена и в `install.sh`, и в `install.bat`;
      сравнение версий и «устарел ли `node_modules`» в `install.bat`
      сделано через `node -e` (delayed на сам Node), а НЕ через
      строковые/датовые сравнения в чистом batch — формат даты `%~tA`
      зависит от региональных настроек Windows («18.08.2026 9:51» на
      русской локали против «08/18/2026 9:51 AM» на английской), и
      наивное сравнение таких строк ненадёжно;
      · сбой `npm install` (нет интернета, прокси блокирует registry)
      раньше не проверялся — скрипт бодро писал «Зависимости установлены»
      независимо от реального результата, и ошибка всплывала только
      косвенно, при старте сервера с непонятным «Cannot find module».
      Теперь код возврата проверяется, сообщение прямо называет частые
      причины;
      · проверка «нужно ли переустанавливать» была завязана на
      существование ровно одного пакета (`node_modules/express`) — если
      кто-то добавил новую зависимость в `package.json` и не запустил
      `npm install` заново, `start.sh`/`start.bat` этого бы не заметили.
      Теперь сравнивается время изменения `package-lock.json` против
      `node_modules` (`-nt` в bash, `fs.statSync().mtimeMs` через `node -e`
      в batch — та же причина избегать batch-дат, что выше);
      · `test.sh`/`test.bat` дублировали часть проверок — переписаны на
      вызов `install.sh --from-start`/`install.bat --from-start` вместо
      третьей копии одной и той же логики;
      · все три `.bat`-файла были на английском, все три `.sh` — на
      русском (унаследовано от исходного `start.bat`) — при русской
      локали пользователя это чистая несогласованность. Все сообщения в
      `.bat`-файлах переведены на русский.
      Проверено: `install.sh`/`test.sh`/`start.sh` — полный цикл с нуля
      (в т.ч. симуляция сбоя npm через недоступный registry — понятная
      ошибка, ненулевой код возврата, а не ложный успех); JS-сниппеты из
      `.bat`-файлов (версия, сравнение времени модификации, кириллица в
      сообщении об ошибке) провалидированы напрямую через `node -e` —
      сам JS одинаков на Windows и Linux, различается только batch-обвязка
      вокруг него, которую здесь протестировать негде.
