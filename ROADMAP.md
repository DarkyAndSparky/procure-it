# Roadmap — procure-it

Статус: ✅ Выполнено · 🔴 Приоритет · 🟡 Следующий приоритет · 🔵 Планируется · 💡 Идея

Текущая версия: **26w34-b07** (см. `CHANGELOG.md`).

Цикл 26w32→26w34 — три раунда аудита: безопасность (три независимых
прохода), бэкапы, производительность — плюс ревизия install/start/test-
скриптов и финальный чек-лист перед первым релизным тегом.

## 🔍 Ручной аудит перед мерджем dev→main + первый e2e-слой — закрыт

Инициировано вручную пользователем («готовлюсь к мерджу в main, надо
обкатать глубокими тестами»), не автоматическим циклом. Два шага: сперва
e2e-каркас (Playwright) поверх существующих unit/интеграционных тестов,
затем — при подготовке e2e к прогону через реальный сервер — ручной
построчный аудит `src/`+`public/js/`, попутно найдено и закрыто два
самостоятельных пункта, оба независимо от e2e.

- [x] **E2e-тесты на Playwright** (`e2e/`, `playwright.config.js`) —
      первый слой, гоняющий настоящий Chromium против настоящего сервера
      (не HTTP напрямую, как `test/http-*.test.js`, и не отдельные
      функции, как остальные unit-тесты). Сеттап-проект заводит
      admin/operator/viewer через API один раз на весь прогон
      (`auth.setup.js`), остальные тесты переиспользуют сохранённый
      `storageState` (токен в `localStorage` — сессия не в куках) вместо
      повторного прохождения формы логина на каждый файл. Покрытие:
      логин/гостевой режим/выход, организации (создание, дубликат
      короткого названия, редактирование, удаление — с проверкой
      синхронизации с селектом на форме заявки), полный цикл заявки
      (создание с проверкой формулы наценки прямо в форме → сохранение →
      поиск в реестре → смена статуса → редактирование с пересчётом
      суммы → удаление), ролевые границы — не только «эта кнопка
      скрыта», но и что сервер реально отдаёт 403/400 на прямой запрос в
      обход UI (self-demotion guard, попытка создать организацию от
      viewer и т.п.). Важная находка по пути: приложение всегда поднимает
      HTTPS с самоподписанным сертификатом (см. `server.js`/`certs.js`),
      рабочего plain-HTTP режима нет вообще — конфиг Playwright должен
      об этом знать (`ignoreHTTPSErrors`), иначе не подключится вообще ни
      к чему. Требует `npx playwright install chromium` перед первым
      прогоном — браузер не входит в `npm install`.
- [x] **`src/config.js` — `PROCURE_DATA_DIR`** — опциональная переменная
      окружения для изоляции e2e-прогона от `data/` репозитория. Без неё
      e2e при локальном запуске писал бы прямо в рабочую БД разработчика.
      Не задана — поведение не меняется.
- [x] **Stored XSS через поле «ед. изм.» позиции** (`registry.js`,
      `buildDetailHtml()`) — единственное место в детали заявки, где
      значение из БД шло в `innerHTML` без `esc()`, при том что все
      соседние поля рядом были экранированы. Поле — свободный текстовый
      инпут в форме заявки, доступный любому operator/admin. Итог:
      сохранённая заявка с HTML-обработчиком события в поле «ед.»
      выполняла код в браузере ЛЮБОГО пользователя, развернувшего эту
      заявку в реестре — включая admin. Токен сессии в `localStorage`, не
      в httpOnly-куке → прямая эскалация привилегий (кража admin-токена
      оператором). CSP (`scriptSrc`/`scriptSrcAttr` содержат
      `'unsafe-inline'` — нужно для многочисленных `onclick=` в текущей
      вёрстке) от этого не защищает. Исправление — одна строка (`esc()`
      вокруг `p.unit`). Найдено при ручном построчном аудите всех
      `innerHTML`-сайтов в `public/js/`, не автотестами — стоит держать в
      уме при следующих ручных проходах: остальные найденные места все
      были экранированы правильно, это была единственная брешь.
- [x] **`total`/`totalPurchase` заявки принимались от клиента без
      проверки** — прошлый раунд аудита (`26w34-b01`) добавил только
      логирование расхождения (`logTotalsMismatch`), решение «что
      делать» сознательно отложил. Решение принято: сервер сам считает
      обе суммы из `positions` (`calcRowPricing` — общий модуль формулы
      для браузера и Node) и игнорирует то, что прислал клиент в этих
      двух полях — подделать сумму заявки прямым API-запросом в обход
      формы больше нельзя. Позиционные суммы внутри каждой строки
      (`purchaseSum`/`sellPerUnit`/`sellSum`) не тронуты — по-прежнему
      зеркалят то, что видел пользователь в форме; их пересчёт на
      сервере — отдельная, более крупная задача, не обязательная для
      закрытия именно этой дыры. Расхождение всё ещё логируется —
      полезный сигнал о рассинхронившейся версии фронтенда, просто
      больше не единственная защита. Проверено вживую: `POST` с `total:
      1` на заявку суммой 105000 ₽ — сервер сохранил и вернул `105000`.
      Регресс на 58 существующих unit-тестах — все проходят без
      изменений.
- [x] **`docs/index.html` — расхождение с реальностью** — раздел
      «Автотесты» описывал `test/http-functional.test.js` и
      `test/http-security.test.js`, которых в репозитории физически нет
      (9 реальных файлов в `test/` — ни один не называется так). Похоже
      на документацию, написанную для планового следующего шага и
      оставленную как есть. Заменено на описание того, что реально
      есть: unit-тесты + новый e2e-слой на Playwright.

**Не сделано в рамках этого прохода** (не заблокировано, но заслуживает
отдельного решения, не части одной этой правки):
- [ ] Позиционные суммы (`purchaseSum`/`sellPerUnit`/`sellSum` внутри
      каждой строки `positions`) по-прежнему принимаются от клиента без
      пересчёта — только суммы уровня заявки теперь считает сервер. Если
      понадобится закрыть и это — придётся тащить на сервер весь
      `calcRowPricing`-пайплайн для каждой строки, включая
      распределение доли доставки, и переписывать `positions` целиком
      перед сохранением, не только два top-level поля.
- [ ] E2e ни разу не прогонялся через настоящий Playwright/Chromium — в
      среде, где писался код, недоступен `cdn.playwright.dev` (список
      разрешённых доменов ограничен npm/github/pypi). Вместо этого все
      сценарии и API-контракты, на которые опираются тесты, проверены
      вручную живыми `curl`-запросами к реально поднятому серверу — но
      финальная сверка через настоящий браузер (селекторы, тайминги,
      реальные клики) — нет. Первый прогон `npm run test:e2e` у
      пользователя может вскрыть мелкие несостыковки в селекторах.
- [ ] CI (`.github/workflows/ci.yml`) по-прежнему не гоняет ни
      `npm test`, ни `npm run test:e2e` — отмечено ещё в прошлых циклах,
      не входило в согласованный на этот раз объём работы (пользователь
      предпочитает прогонять тесты вручную).

## 🐛 Аудит корректности перед слиянием dev→main — закрыт

Системный проход по `src/` (не безопасность и не производительность — они
закрыты в отдельных циклах выше/ниже) — логические ошибки, необработанные
исключения, пробелы валидации, гонки. Пять находок, все исправлены и
проверены вживую (не только тестами).

- [x] **`POST /api/restore` не был транзакционным** — `DELETE FROM
      users/orgs/requests` выполнялся до проверки, что новые данные вообще
      вставятся. При несовместимом бэкапе таблица могла остаться пустой —
      для `users` это означало полную блокировку входа без единого способа
      восстановиться, кроме прямого доступа к файлу БД. Ответ API также
      врал: `restored: orgs.length` — размер входного массива, а не число
      реально вставленных строк. Вся операция теперь — одна SQLite-
      транзакция (`BEGIN`/`COMMIT`/`ROLLBACK` — sql.js их полноценно
      поддерживает, проверено отдельным скриптом до правки). `saveDb()`
      один раз в конце вместо на каждую вставленную строку — заодно и
      быстрее (раньше был full db.export()+writeFileSync на КАЖДУЮ
      строку восстанавливаемых данных). Попутно найден и исправлен
      отдельный, независимый баг в том же коде: `o.prefix` без
      `||''`-фолбэка ронял вставку организации на `undefined` в SQL-
      параметре (все остальные необязательные поля фолбэк имели, это —
      нет). Добавлена явная проверка обязательных полей (org: full/short,
      request: name) — пропускаются с логом причины, а не проваливаются
      на undefined в бинд-параметре. Покрыто 7 тестами
      (`test/backup-restore.test.js`) — полностью невалидный `users` не
      обнуляет таблицу, валидный — заменяет корректно, org/request без
      обязательных полей пропускаются не задевая остальные, restore без
      admin-роли отклоняется. Проверено и живым curl-сценарием: битый
      `users` (без password) → `admin` не удалён, вход по-прежнему
      работает.
- [x] **HTTP-запросы к вебхукам (Bitrix, статус) — без таймаута.**
      `POST /api/send-bitrix` ждёт ответ синхронно в обработчике —
      недоступный/зависший вебхук вешал запрос навсегда, пользователь
      получал вечную загрузку без единого шанса на ошибку. Добавлен
      таймаут 15с. Проверено на реально зависающем тестовом HTTP-сервере
      (принимает соединение, никогда не отвечает) — таймаут сработал
      ровно через 15.0с с понятным сообщением, промис корректно
      отклонился.
- [x] **`rowToRequest()` — `JSON.parse(positions)` без try/catch.**
      Функция вызывается для каждой строки на `GET /api/requests` (список
      реестра) — один битый JSON в `positions` ронял загрузку ВСЕГО
      списка для всех пользователей, не только одну эту заявку. try/catch
      с fallback на `[]` и предупреждением в лог с id конкретной заявки;
      отдельно проверяется, что после парсинга получился именно массив
      (а не строка/число/объект — иначе дальше `.map`/`.reduce` упали бы
      TypeError'ом в произвольном месте фронтенда). Проверено: испортил
      `positions` напрямую в файле БД (сервер выключен — иначе sql.js
      просто перезапишет правку своим in-memory состоянием при следующей
      записи), перезапустил сервер — `GET /api/requests` отдаёт `200`, не
      `500`, битая заявка просто без позиций вместо падения всего
      эндпоинта.
- [x] **`PUT /requests/:id` не валидировал позиции**, хотя `POST
      /requests` — валидировал (тип `name`, `qty>=0`, число в цене).
      Через редактирование существующей заявки можно было сохранить то,
      что create отклонил бы. Вынесено в общую `validatePositions()` —
      использует и create, и update, дальше эти две проверки не смогут
      разойтись снова. Проверено: некорректный `qty` (строка, отрицательное
      число) теперь даёт `400` и на create, и на update; корректные данные
      по-прежнему проходят.
- [x] **Имя файла автобэкапа было с точностью до минуты**
      (`toTimeString().slice(0,5)` — только часы:минуты). Ручной бэкап
      админом в ту же минуту, что и плановый автобэкап (или два быстрых
      ручных подряд), тихо перезаписывал один снапшот другим через
      `fs.writeFileSync`. Добавлены секунды в имя файла. Проверено:
      ротация старых бэкапов работает по `fs.statSync().mtime`, не
      парсит имя файла — смена формата имени безопасна. Два вызова
      `GET /api/backup/db` подряд (с паузой 2с) теперь дают два разных
      файла на диске, не один.
- [x] **Расширены тесты для находок этого аудита** — часть фиксов выше
      (таймаут вебхука, уникальность имени бэкапа, `validatePositions`)
      проверялась только вручную через curl, без единого автотеста.
      Добавлено 22 теста: `test/requests-validation.test.js` (16 —
      `validatePositions`/`rowToRequest`, включая границы: `qty=0`,
      битый JSON, JSON валиден но не массив), `test/bitrixService.test.js`
      (4 — таймаут `postJson` на реально зависающем тестовом сервере,
      успешный/не-JSON ответ, мгновенный `ECONNREFUSED`),
      `test/backupService.test.js` (2 — регрессия на саму коллизию имени,
      формат имени с секундами). Таймаут в `postJson()` вынесен в
      необязательный параметр (`timeoutMs`, дефолт — прежние 15000) — тест
      таймаута использует короткую отсечку (200мс), не растягивая
      `npm test` на 15+ секунд ради одного теста; `validatePositions`
      экспортирован как свойство роутера (`router.validatePositions`),
      без изменения `module.exports = router`. Итог: **58 тестов**
      (было 36).
- [x] **«О системе» показывала любой пакет с более новой мажорной версией
      на npm как «устаревший»** — замечено пользователем в контексте
      вопроса «мы на LTS, а проверка по последним билдам?». `npm outdated
      --json` уже отдавал и `wanted` (максимум в рамках собственного
      `^`-диапазона в `package.json`), и `latest` (абсолютный последний
      релиз на npm, включая мажоры, от которых сознательно отказались —
      Express 4→5, см. раздел про производительность выше), но фронтенд
      показывал только `latest`, всегда жёлтым, для любого пакета, где
      `latest !== current` — то есть пакет, полностью актуальный В РАМКАХ
      диапазона, выглядел как «пора обновить» точно так же, как реально
      отставший от диапазона. Разделено: `current !== wanted` — реальная
      просрочка, предупреждение с `wanted`; `wanted !== latest` при
      `current === wanted` — нейтральная информация «есть Х.х», не
      тревога. Отдельно проверено: сама проверка версии Node.js
      (`check-node-version.js`) этим не страдает — там только нижняя
      граница (`>=18.x`), верхнего предела или сверки с «последним
      билдом» нет и не было. Проверено на реальных данных проекта: было
      «5 устаревших», стало «1» (только `sql.js`, у которого `current`
      реально ниже `wanted` — `1.14.1` вместо `1.14.2`).
- [x] `scripts/sync-version.js` не синхронизировал `Dockerfile`'s `LABEL
      org.opencontainers.image.version` — правился вручную при каждом
      бампе версии (пункт был в backlog ниже). Добавлена та же логика,
      что уже была для `docker-compose.yml`. Проверено: специально сбил
      версию в `Dockerfile` на произвольную строку, прогнал
      `npm run version:sync` — поправил; повторный прогон на уже
      синхронизированном файле — «0 изменено», не ложное срабатывание.

## 🔒 Аудит безопасности и бэкапов — закрыт

Все находки закрыты в коде и проверены вручную живыми запросами к серверу
(не только `npm test`), не только через тесты «на бумаге».

**Бэкапы:**
- [x] Секреты вебхуков (`bitrixWebhook`, `statusWebhook`) утекали в
      скачиваемый JSON-бэкап — исключены из выгрузки, как и `networkPass`
      (`SECRET_SETTINGS` в `backup.js`). Проверено: бэкап с настроенными
      вебхуками их не содержит.
- [x] `POST /api/restore` не валидировал роль пользователя по белому
      списку `['viewer','operator','admin']`, в отличие от обычного
      создания пользователя — теперь та же проверка. Проверено:
      подсунутая роль `superadmin` в бэкапе не создаёт пользователя.
- [x] Rate limit на `GET /api/backup` (JSON) выровнен с `/backup/db` —
      оба под `strictLimiter`.

**Безопасность (три независимых прохода):**
- [x] Command injection через `exec()` при открытии папки заявки —
      название заявки (обычное поле operator) санитизировалось только под
      правила ФС, не под shell-метасимволы. Переведено на `execFile`/
      `execFileSync` с массивом аргументов (Linux/macOS `openFolder`,
      Windows `mountSmbIfNeeded`) — путь идёт напрямую в ОС, без shell.
      Проверено на реальном payload в названии заявки
      (`Заявка $(touch /tmp/marker)`) — не выполняется, попадает в имя
      папки как текст.
- [x] Общая PBKDF2-соль на всех пользователей → соль-на-пользователя
      (`users.salt`, `crypto.randomBytes(16)`). Старые записи (общая
      PBKDF2-соль и самый старый голый SHA-256) автоматически мигрируют
      при следующем успешном входе, без принудительного сброса пароля
      всем разом. Покрыто автотестами (`test/auth.test.js`, 7 тестов) —
      этой логики раньше не было вообще, хотя это ровно тот код, который
      легко тихо сломать следующей правкой.
- [x] **Третий проход, по свежему коду с прошлого раунда:** сравнение
      секретов через обычное `===` вместо timing-safe. Разобрано по
      конкретным местам, не одной кистью:
      · сравнение ХЭШЕЙ паролей (`hashPassword(...) === storedHash`) —
      технически не эксплуатируемо (PBKDF2 — однонаправленная функция с
      лавинным эффектом, соседние пароли дают несвязанные хэши, «нащупать»
      пароль по времени сравнения хэша нельзя — нет градиента). Но
      timing-safe сравнение стоит буквально ничего, применено и здесь —
      не приходится объяснять каждому будущему читателю кода, почему в
      одном месте `===` безопасен, а в другом нет;
      · `password === LEGACY_PASSWORD` в `findUserByCredentials` — это
      уже реальный, а не теоретический риск: сравнивается СЫРОЙ секрет
      (человеком заданный пароль в `.env`, может быть коротким) с
      пользовательским вводом напрямую, без хэширования — классический
      уязвимый паттерн. Единая `timingSafeStringEqual()` (`crypto.js`,
      обёртка над `crypto.timingSafeEqual`) применена везде, где
      сравнивается что-то пользовательское с секретом на сервере.
      Проверено вживую: `LEGACY_PASSWORD`-режим (верный/неверный пароль),
      смена пароля (верный/неверный текущий) — оба сценария работают как
      раньше; плюс 4 новых юнит-теста на саму функцию сравнения
      (совпадение / несовпадение / разная длина / пустые значения).
- [x] `requireSafeId` добавлен на GET-роуты файлов
      (`signed-spec`/`invoice-file`) — раньше был только на POST.
- [x] `GET /api/system-info`(`/outdated`) сужен до `adminOnly` — был
      доступен operator, хотя страница «О системе» в UI и так видна
      только admin.
- [x] `Date.now()` как id организаций/заявок → `crypto.randomUUID()` —
      исключена теоретическая гонка при параллельном создании.
- [x] Сервер логирует расхождение между `total`/`totalPurchase`,
      присланными клиентом, и пересчитанными из `positions` той же
      формулой (`pricing-core.js`) — не блокирует сохранение, только
      предупреждение в лог (наблюдаемость, не enforcement).

- [ ] **`.env` закоммичен в git, несмотря на `.gitignore`** — файл уже
      отслеживается (закоммичен раньше, чем добавили правило), поэтому
      `.gitignore` для него сейчас не работает. Только ручное действие:
      `git rm --cached .env` — не входит ни в один поставляемый архив.

## ⚡ Аудит производительности — находки задокументированы, действий не требуется

Замерено на реалистичных данных (сгенерированы синтетически, 5 полей на
позицию), не оценено на глаз. **Ничего из этого не тормозит на текущих
объёмах** — раздел информационный, на будущее, если данные вырастут на
порядок.

| Что | Замер | Вывод |
|---|---|---|
| Одна запись (`db.export()`+`writeFileSync`) при 100 / 1000 / 5000 заявок в базе | 1.2 / 5.2 / 5.3 мс | `sql.js` пересобирает и пишет **всю** БД на каждую запись (не точечно, как «настоящий» SQLite) — блокирует event loop синхронно на время записи. На локальном SSD это доли мс на реалистичных объёмах. Риск — если БД когда-нибудь окажется на медленном диске (сетевая папка, HDD под нагрузкой); сейчас БД всегда пишется локально, не завязана на `backupFolder` |

| Генерация `.docx` спецификации | — | Асинхронно, один документ на один HTTP-запрос, не блокирует сервер для остальных |

| Рендер реестра | — | Уже с server-side пагинацией (100/до 500), детали строки — лениво по клику (сделано в одном из прошлых циклов), N+1-запросов при загрузке нет |

      причём ломались не только `echo`, но и **`rem`-комментарии** (в
      одном из сообщений виден обрывок слова из комментария в `test.bat`).
      Вывод: `chcp 65001` меняет кодировку консольного ввода-вывода, но
      не гарантирует, что сам парсер `cmd.exe` читает БАЙТЫ batch-файла
      как UTF-8 при токенизации команд — на части версий/консолей Windows
      это до сих пор ломается, независимо от того, что именно на строке:
      выводимый текст или комментарий. Протестировать эмпирически на
      реальной Windows была возможности (среда без Windows), синтаксис/
      JS-сниппеты проверялись отдельно, но саму эту проблему поймать
      заранее было нельзя.

      **включая комментарии**, не только видимый текст (`file` подтверждает
      «ASCII text», не «UTF-8 text»). `.sh`-версии кириллицу сохранили —
      той же проблемы там нет в принципе: bash токенизирует байтовые
      потоки равномерно, метасимволы шелла (`;`, `|`, `&`, кавычки) все в
      диапазоне ASCII, конфликтовать с многобайтовыми UTF-8-
      последовательностями кириллицы им негде. Это Windows-специфичная
      ловушка, не общая для обеих платформ.
- [x] **Кириллица в `.bat` вернулась — по образцу рабочего паттерна
