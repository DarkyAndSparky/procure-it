## 🔒 Аудит безопасности и бэкапов — закрыт

Все находки закрыты в коде и проверены вручную живыми запросами к серверу
(не только `npm test`), не только через тесты «на бумаге».

**Бэкапы:**
- [x] Секреты вебхуков (`bitrixWebhook`, `statusWebhook`) утекали в
      скачиваемый JSON-бэкап — исключены из выгрузки, как и `networkPass`
      (`SECRET_SETTINGS` в `backup.js`). Проверено: бэкап с настроенными
      вебхуками их не содержит.
- [x] `POST /api/restore` не валидировал роль пользователя по белому
      списку `['viewer','operator','admin']`, в отличие от обычного
      создания пользователя — теперь та же проверка. Проверено:
      подсунутая роль `superadmin` в бэкапе не создаёт пользователя.
- [x] Rate limit на `GET /api/backup` (JSON) выровнен с `/backup/db` —
      оба под `strictLimiter`.

**Безопасность (три независимых прохода):**
- [x] Command injection через `exec()` при открытии папки заявки —
      название заявки (обычное поле operator) санитизировалось только под
      правила ФС, не под shell-метасимволы. Переведено на `execFile`/
      `execFileSync` с массивом аргументов (Linux/macOS `openFolder`,
      Windows `mountSmbIfNeeded`) — путь идёт напрямую в ОС, без shell.
      Проверено на реальном payload в названии заявки
      (`Заявка $(touch /tmp/marker)`) — не выполняется, попадает в имя
      папки как текст.
- [x] Общая PBKDF2-соль на всех пользователей → соль-на-пользователя
      (`users.salt`, `crypto.randomBytes(16)`). Старые записи (общая
      PBKDF2-соль и самый старый голый SHA-256) автоматически мигрируют
      при следующем успешном входе, без принудительного сброса пароля
      всем разом. Покрыто автотестами (`test/auth.test.js`, 7 тестов) —
      этой логики раньше не было вообще, хотя это ровно тот код, который
      легко тихо сломать следующей правкой.
- [x] **Третий проход, по свежему коду с прошлого раунда:** сравнение
      секретов через обычное `===` вместо timing-safe. Разобрано по
      конкретным местам, не одной кистью:
      · сравнение ХЭШЕЙ паролей (`hashPassword(...) === storedHash`) —
      технически не эксплуатируемо (PBKDF2 — однонаправленная функция с
      лавинным эффектом, соседние пароли дают несвязанные хэши, «нащупать»
      пароль по времени сравнения хэша нельзя — нет градиента). Но
      timing-safe сравнение стоит буквально ничего, применено и здесь —
      не приходится объяснять каждому будущему читателю кода, почему в
      одном месте `===` безопасен, а в другом нет;
      · `password === LEGACY_PASSWORD` в `findUserByCredentials` — это
      уже реальный, а не теоретический риск: сравнивается СЫРОЙ секрет
      (человеком заданный пароль в `.env`, может быть коротким) с
      пользовательским вводом напрямую, без хэширования — классический
      уязвимый паттерн. Единая `timingSafeStringEqual()` (`crypto.js`,
      обёртка над `crypto.timingSafeEqual`) применена везде, где
      сравнивается что-то пользовательское с секретом на сервере.
      Проверено вживую: `LEGACY_PASSWORD`-режим (верный/неверный пароль),
      смена пароля (верный/неверный текущий) — оба сценария работают как
      раньше; плюс 4 новых юнит-теста на саму функцию сравнения
      (совпадение / несовпадение / разная длина / пустые значения).
- [x] `requireSafeId` добавлен на GET-роуты файлов
      (`signed-spec`/`invoice-file`) — раньше был только на POST.
- [x] `GET /api/system-info`(`/outdated`) сужен до `adminOnly` — был
      доступен operator, хотя страница «О системе» в UI и так видна
      только admin.
- [x] `Date.now()` как id организаций/заявок → `crypto.randomUUID()` —
      исключена теоретическая гонка при параллельном создании.
- [x] Сервер логирует расхождение между `total`/`totalPurchase`,
      присланными клиентом, и пересчитанными из `positions` той же
      формулой (`pricing-core.js`) — не блокирует сохранение, только
      предупреждение в лог (наблюдаемость, не enforcement).

- [ ] **`.env` закоммичен в git, несмотря на `.gitignore`** — файл уже
      отслеживается (закоммичен раньше, чем добавили правило), поэтому
      `.gitignore` для него сейчас не работает. Только ручное действие:
      `git rm --cached .env` — не входит ни в один поставляемый архив.

## ⚡ Аудит производительности — находки задокументированы, действий не требуется

Замерено на реалистичных данных (сгенерированы синтетически, 5 полей на
позицию), не оценено на глаз. **Ничего из этого не тормозит на текущих
объёмах** — раздел информационный, на будущее, если данные вырастут на
порядок.

| Что | Замер | Вывод |
|---|---|---|
| Одна запись (`db.export()`+`writeFileSync`) при 100 / 1000 / 5000 заявок в базе | 1.2 / 5.2 / 5.3 мс | `sql.js` пересобирает и пишет **всю** БД на каждую запись (не точечно, как «настоящий» SQLite) — блокирует event loop синхронно на время записи. На локальном SSD это доли мс на реалистичных объёмах. Риск — если БД когда-нибудь окажется на медленном диске (сетевая папка, HDD под нагрузкой); сейчас БД всегда пишется локально, не завязана на `backupFolder` |
| Текстовый поиск (`LIKE` по 5 колонкам, включая JSON `positions`) при 5000 заявках | 22 мс | Full scan — индекс с ведущим `%` в LIKE в принципе не работает. Отдельный `COUNT(*)` для пагинации — **второй** такой же full scan на тот же запрос (17 мс) |
| Обычная выборка без фильтров / с фильтром по `org_id` (есть индекс) | 5 / 11 мс | В порядке |
| Генерация `.docx` спецификации | — | Асинхронно, один документ на один HTTP-запрос, не блокирует сервер для остальных |
| Экспорт в Excel | — | Целиком в браузере пользователя, не трогает сервер вообще |
| Рендер реестра | — | Уже с server-side пагинацией (100/до 500), детали строки — лениво по клику (сделано в одном из прошлых циклов), N+1-запросов при загрузке нет |

Если возвращаться к этому разделу: первое, что начнёт проседать при
кратном росте данных — текстовый поиск (двойной full scan). Точечная
идея на будущее — не считать точный `COUNT(*)` при активном текстовом
поиске (показывать «500+» вместо точного числа), но это меняет UX
пагинации, поэтому не делалось без отдельного решения.

## 🛠️ Инфраструктура сборки и запуска — закрыто

- [x] `install.sh`/`install.bat` — установка зависимостей без запуска
      сервера, выделены из `start.*`. `start.*` теперь вызывают
      `install.* --from-start` вместо дублирования логики.
- [x] `test.sh`/`test.bat` — отдельный запускатор тестов, тоже больше не
      дублирует install-логику (`install.* --from-start`).
- [x] `playwright` был в `dependencies`, хотя нигде не используется —
      перенесён в `devDependencies`. Проверено: `npm ci --omit=dev` (как
      в Dockerfile) реально его пропускает, `npm test` на таком инсталле
      всё равно проходит все тесты.
- [x] `.dockerignore` — явные правила на `install.*`/`test.*`/`test/`.
- [x] `start.bat` открывал браузер по фиксированному таймеру параллельно
      со стартом сервера (гонка — если старт занимал дольше 3с, браузер
      открывался раньше готовности). Перенесено в колбэк `.listen()` в
      `server.js`, управляется `PROCURE_AUTO_OPEN=1` (только для
      `start.bat`, не влияет на Docker/systemd-запуски).
- [x] `start.bat` требовал двух запусков после свежей установки —
      исходный вызывал `npm install` (batch-скрипт) без `call`, что в
      Windows batch обрывает родительский скрипт сразу после выполнения
      дочернего. Исправлено (`call npm install`), плюс `cd /d "%~dp0"` и
      CRLF-окончания во всех трёх `.bat`-файлах.
- [x] Ревизия install/start/test под русскую локаль:
      · добавлена проверка минимальной версии Node.js (`engines.node`) —
      раньше отсутствовала вообще;
      · сравнение версий/дат в `.bat` — через `node -e`, не через batch
        (формат `%~tA` зависит от региональных настроек Windows —
        «18.08.2026 9:51» на русской локали vs «08/18/2026 9:51 AM» на
        английской, наивное сравнение ненадёжно);
      · сбой `npm install` (нет интернета) теперь ловится явно, вместо
        ложного «Зависимости установлены»;
      · проверка устаревания зависимостей — по времени изменения
        `package-lock.json` относительно `node_modules`, не по факту
        существования одного пакета.
- [x] **Откачен перевод `.bat`-файлов на русский — сломал их на реальной
      Windows.** Была попытка (см. пункт выше) перевести весь видимый
      текст в `install.bat`/`start.bat`/`test.bat` на русский для
      единообразия с `.sh`, полагаясь на `chcp 65001`. На практике не
      сработало: пользователь сообщил, что оба скрипта падают с ошибками
      вида `'—' is not recognized as an internal or external command` —
      причём ломались не только `echo`, но и **`rem`-комментарии** (в
      одном из сообщений виден обрывок слова из комментария в `test.bat`).
      Вывод: `chcp 65001` меняет кодировку консольного ввода-вывода, но
      не гарантирует, что сам парсер `cmd.exe` читает БАЙТЫ batch-файла
      как UTF-8 при токенизации команд — на части версий/консолей Windows
      это до сих пор ломается, независимо от того, что именно на строке:
      выводимый текст или комментарий. Протестировать эмпирически на
      реальной Windows была возможности (среда без Windows), синтаксис/
      JS-сниппеты проверялись отдельно, но саму эту проблему поймать
      заранее было нельзя.
      Исправление: все три `.bat`-файла переписаны в чистый ASCII —
      **включая комментарии**, не только видимый текст (`file` подтверждает
      «ASCII text», не «UTF-8 text»). `.sh`-версии кириллицу сохранили —
      той же проблемы там нет в принципе: bash токенизирует байтовые
      потоки равномерно, метасимволы шелла (`;`, `|`, `&`, кавычки) все в
      диапазоне ASCII, конфликтовать с многобайтовыми UTF-8-
      последовательностями кириллицы им негде. Это Windows-специфичная
      ловушка, не общая для обеих платформ.
- [x] **Кириллица в `.bat` вернулась — по образцу рабочего паттерна
      пользователя, не наугад.** Пользователь показал два реальных
      `.bat`-файла из своего другого проекта, где кириллица под тем же
      `chcp 65001` работает стабильно. Сравнение выявило конкретные
      отличия от того, что сломалось в b01 (не гипотеза «кириллица вообще
      не работает» — она работает, но не в любой обвязке):
      · разделители-баннеры — простой ASCII `===`, не символы псевдографики
        (`══════`, 3-байтовая UTF-8-последовательность, скопированная из
        стиля баннера `server.js` без учёта, что для `.bat`-файла это
        отдельный источник риска);
      · вся логика проверки версии — в отдельном `.js`-файле, вызывается
        простой командой `node scripts\check-node-version.js` без единого
        спецсимвола на строке `.bat`, а не через `node -e "..."` с кучей
        скобок/кавычек/точек-с-запятой вперемешку с русским текстом
        ошибки на одной строке;
      · только последовательные одиночные `if X (...)`, без `if/else`;
      · без вызова одного `.bat` из другого с передачей флага
        (`call install.bat --from-start`) — небольшое дублирование между
        файлами вместо кросс-файловой связи;
      · литеральные скобки внутри кириллического текста экранированы
        (`^(...^)`), как в образце.
      Добавлены `scripts/check-node-version.js` и `scripts/check-deps-
      fresh.js` — вынесенная в отдельные файлы логика, общая для `.sh` и
      `.bat` (раньше в `.sh` эта же логика была продублирована через
      `node -e`, теперь оба вызывают один и тот же `.js`). Проверено:
      оба хелпера — напрямую (верная/заниженная версия Node, свежие/
      устаревшие зависимости), эмуляция Docker-сборки с новыми файлами,
      полный цикл `install.sh`/`start.sh` на чистом окружении, `npm test`
      29/29. Саму батницу на реальной Windows по-прежнему проверить
      негде — просьба сообщить, если и в этот раз что-то не так.
