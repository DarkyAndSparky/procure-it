# ROADMAP_MIGRATION.md — переезд на новый стек

Отдельный документ, не часть `ROADMAP_Q4.md` (тот — про фичи текущего
квартала, этот — про инфраструктурный переезд, может растянуться дольше
одного квартала). Каждый шаг — один коммит, одна запись в `CHANGELOG.md`,
один `npm run bump`. Ничего крупнее одного файла/одной ответственности за
шаг — так можно останавливаться и продолжать в любой момент, без
«зависших» промежуточных состояний.

Проект в длительной бете, классического релиза ещё не было — откат не
критичен, поэтому без отдельной ветки-миграции и без стадии заморозки:
работаем прямо в `dev`, шаг за шагом, тесты — регрессионная сетка.

Express остаётся 4-й версии — не в этом плане.
Бенчмарки/CPU-профилирование — не в этом плане, не ваш масштаб.

## Stage 1 — CommonJS → ESM (без единого изменения в работе с БД)

Отдельно от Stage 2 намеренно: два независимых изменения в одном шаге —
если что-то сломается, не будет понятно, из-за модульной системы это
или из-за БД.

1.1. `package.json` → добавить `"type": "module"`
1.2. `server.js`: `require(...)` → `import ...`, `module.exports` (если
     есть) → `export`
1.3. `src/db/*.js` (4 файла, `connection.js`/`schema.js`/`audit.js`) —
     перевести require/exports → import/export. Прогнать `npm test`
     после каждого файла, не пачкой
1.4. `src/services/*.js` (5 файлов) — по одному, от меньшего к
     большему: `bitrixService.js`(93) → `emailService.js`(136) →
     `docxService.js`(288) → `fileLayoutService.js`(504) →
     `backupService.js`(125, реально маленький, просто оказался
     не по размеру в этом месте списка — сверить точный порядок перед
     стартом)
1.5. `src/routes/*.js` (8 файлов) — по одному, от меньшего к большему:
     `docx.js`(25) → `bitrix.js`(33) → `files.js`(233) →
     `settings.js`(243) → `orgs.js`(244) → `backup.js`(313) →
     `auth.js`(325) → `requests.js`(519)
1.6. `test/*.js` (15 файлов) — `node:test` поддерживает ESM нативно,
     перевести импорты
1.7. `scripts/*.js` — не мигрировать на ESM: это разовые CLI-утилиты
     вне HTTP-приложения, не обязаны жить в одной модульной системе с
     сервером. Проще: переименовать в `.cjs` (Node уважает расширение
     независимо от `"type"` в `package.json`) и не трогать их
     содержимое вообще
1.8. `public/js/*.js` — **не трогать**. Это браузерный код через
     `<script src>`, к серверной модульной системе отношения не имеет,
     отдельная (и не обязательная) тема
1.9. После каждого файла — `npm test`. После всего блока — ручная
     проверка: `npm start`, открыть в браузере, пройти по 2-3 основным
     экранам (реестр, карточка заявки, dashboard) — раз меняем импорты
      везде, самый дешёвый способ поймать пропущенный `require` — глазами
1.10. Коммит "ESM migration complete" + CHANGELOG + `npm run bump`

## Stage 2 — sql.js → node:sqlite (изолированно, БЕЗ смены внешнего API)

Снаружи (`src/routes/*.js`) ничего не должно измениться — тот же
`query(sql, params)`/`run(sql, params)`. Меняется только то, что под
этой сигнatурой.

2.1. Скопировать реальный `data/zakupki.db` (или тестовый с
     реалистичным объёмом) в `data/zakupki.db.pre-migration-backup` —
     разовая ручная подстраховка, не автоматизировать
2.2. Новый `src/db/connection.js`: `DatabaseSync` из `node:sqlite`
     вместо `sql.js`. Сохранить экспортируемые имена (`initDb`,
     `getDb`, `query`, `run`, `rowToRequest`) — `saveDb` пока оставить
     как no-op с предупреждением в консоли (не удалять экспорт сразу,
     чтобы ничего не упало на вызовах, которые ещё не почищены — почистим
     в 2.4)
2.3. Настроить PRAGMA сразу после открытия: `journal_mode=WAL`,
     `foreign_keys=ON`, `busy_timeout=5000`. `synchronous=NORMAL` —
     отдельным пунктом, подтвердить, что не конфликтует с текущей
     логикой backup (WAL это может задеть — проверить руками)
2.4. Прогнать `npm test` на новом `connection.js` — 97 тестов ловят
     регрессии в самой БД-логике бесплатно
2.5. **Проверка совместимости старого файла БД**: открыть скопированный
     в 2.1 `zakupki.db` через новый `connection.js`, убедиться, что
     существующие данные читаются (SQLite-формат общий, но проверить
     на реальном файле, не гипотетически)
2.6. Пройтись по всем `saveDb()` в `src/routes/*.js` (сейчас — 8 мест)
     и убрать вызовы по одному файлу за раз, тем же порядком, что в
     1.5. Тесты после каждого файла
2.7. Добавить `transaction(callback)` helper в `connection.js`
2.8. Применить `transaction()` к двум реальным местам, где сейчас нет
     атомарности: создание заявки+позиций (`requests.js`) и restore
     (`backup.js`) — не искать другие места «на всякий случай», только
     эти два, они уже были на примете
2.9. Ручная проверка backup/restore на файле из 2.1 — сделать backup,
     сделать restore, сверить, что данные те же
2.10. Коммит + CHANGELOG + `npm run bump`

## Stage 3 — тонкий repository-слой (не полный controllers/services)

Цель — вынести SQL из роутов в отдельные файлы, не более. Никакого
`controllers/`+`services/`+`repositories/` одновременно — это Stage 4,
опциональный.

Порядок — от простого к сложному, тот же, что в 1.5/2.6, чтобы
обкатать паттерн на маленьком файле прежде чем переносить на большой:

3.1. `src/repositories/orgsRepository.js` — вынести SQL из
     `orgs.js`(244, самый маленький из «настоящих» CRUD-роутов).
     `orgs.js` после этого — только HTTP-слой, вызывает репозиторий
3.2. Тесты, коммит, CHANGELOG, bump
3.3. `src/repositories/filesRepository.js` ← `files.js`(233)
3.4. `src/repositories/settingsRepository.js` ← `settings.js`(243)
3.5. `src/repositories/auditRepository.js` + бэкап-специфичный SQL ←
     `backup.js`(313) — заодно объединить с существующим `db/audit.js`,
     не плодить два места с похожей ответственностью
3.6. `src/repositories/usersRepository.js` ← `auth.js`(325)
3.7. `src/repositories/requestsRepository.js` ← `requests.js`(519,
     самый большой — разбить сам этот шаг на подшаги: сначала CRUD
     заявок, отдельным коммитом — позиции, отдельным — diff/audit-логика
     заявок)
Каждый пункт (3.2–3.7) — свой коммит, не пачкой.

## Stage 4 — controllers/services (опционально, не обязательна)

Рассмотреть только если после Stage 3 репозитории реально мешает
смешение HTTP-логики с бизнес-логикой на практике — не переносить
по инерции из исходного плана. Если через пару спринтов после Stage 3
жизнь и так ощущается нормально — эту стадию можно закрыть как
неактуальную, а не как невыполненную.

## Что осталось за скобками (осознанно)

- Express 5 — снято по вашему решению, не «хотелка», не в этом плане
- Domain-error классы (`AppError`/`ValidationError`/...) — идея
  разумная, но отдельная от переезда на новый стек; можно поднять
  отдельным пунктом в `ROADMAP_Q4.md`, если начнёт реально мешать
  текущий `catch → console.error → return []`
- Бенчмарки старта/памяти/CPU-профилирование — не ваш масштаб
- `.nvmrc`/Volta — дёшево добавить, не требует отдельной стадии,
  можно сделать одной строкой в Stage 0 заодно с остальным
