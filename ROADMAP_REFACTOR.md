## Stage 1 — Зависимости: свежесть без риска

Разделяю на «безопасно бампнуть прямо сейчас» (патч/минор, тот же
мажор) и «требует отдельного решения» (мажорный скачок, вероятны
breaking changes) — не мешаю их в одном коммите.

### 1.1 — Патч/минор-бампы, один коммит на всё
```
compression   1.7.4 → 1.8.2
morgan        1.10.0 → 1.12.1
sql.js        1.10.3 → 1.14.2   (временно — см. Stage 3)
express       4.18.2 → 4.22.3   (патч на 4.x, до Stage 3.5 — см. ниже)
@playwright/test / playwright  1.62.1 → 1.63.0
```
`npm update`, затем `npm test`, затем `npm run test:e2e` (у вас, не
у меня — браузер только на вашей машине). Один коммит, одна запись
CHANGELOG.

### 1.2 — Мажорные бампы, каждый ОТДЕЛЬНЫМ коммитом, с чтением changelog библиотеки перед апдейтом
Не бампать вслепую — каждая из них меняет публичный API:
- `express-rate-limit` 7 → 8 — проверить сигнатуру `limit()`/`keyGenerator`, у вас кастомная логика в rate-limit мидлварах. Заодно свериться с Express 5 (Stage 3.5) — убедиться, что 8-я версия сама совместима с Express 5, раз апгрейдим оба
- `docx` 8 → 9 — генератор спецификаций (`docxService.js`, 288 строк) активно использует API этой библиотеки; апдейт может потребовать правок в построении документа, не только в `package.json`
- `selfsigned` 2 → 5 — используется в генерации HTTPS-сертификата для локального запуска; проверить, не сменился ли API `generate()`
- `nodemailer` 9 → 10 — `emailService.js`; проверить transport-опции

Каждый: апдейт → `npm test` → ручная проверка конкретной фичи (сгенерировать docx, отправить тестовое письмо, поднять HTTPS) → коммит → CHANGELOG → bump.

## Stage 3 — sql.js → node:sqlite

(Тоже перенесено без изменений сути — решение принято.)

**`node:sqlite` — промежуточный шаг, не конечная точка.** Если после
переезда обнаружится, что чего-то не хватает (кастомные SQLite-функции,
расширения, более тонкий контроль над prepared statements, или сам
`node:sqlite` останется не до конца стабильным в той версии Node, на
которой реально сидите) — следующий кандидат **`better-sqlite3`**. Не
делать сейчас проактивно: `node:sqlite` закрывает исходную проблему
(«без C++ при установке») полностью, `better-sqlite3` добавлял бы
обратно именно ту головную боль (нативная компиляция), от которой
уходим. Пересматривать только по факту нехватки, не заранее.

3.1. Скопировать реальный `data/zakupki.db` для проверки на настоящих данных, не только на пустой БД
3.2. Новый `src/db/connection.js` на `DatabaseSync`, тот же внешний интерфейс (`query()`/`run()`)
3.3. PRAGMA: `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`
3.4. Прогнать тесты на новом `connection.js`
3.5. Проверить совместимость реального файла БД из 3.1
3.6. Убрать `saveDb()` из `src/routes/*.js`, по одному файлу, тем же порядком, что в 2.5
3.7. `transaction()` helper + применить к созданию заявки+позиций и к restore
3.8. Ручная проверка backup/restore на файле из 3.1

## Stage 3.5 — Express 4 → 5

Возвращено в план по вашему явному решению — раньше откладывалось как
не имеющее срочной причины, теперь делаем осознанно, с полным списком
рисков на виду, не «между делом» вместе с чем-то ещё.

**Почему отдельным этапом, не вместе со Stage 2/3:** апгрейд меняет
поведение самого фреймворка — если что-то сломается, нужно понимать,
что именно из-за Express 5, а не из-за ESM или БД, которые меняются
рядом. Делать **после** Stage 2 (ESM) и Stage 3 (node:sqlite) — Express
5 такого дедлайна не имеет, а вот дважды прогонять регрессию (сначала
на ESM+БД, потом ещё раз на Express) дороже, чем сделать по одному
изменению за раз в понятном порядке.

Известные точки риска (см. официальный migration guide Express 5 перед
стартом — список ниже не заменяет его, а фиксирует то, что специфично
для вашего кода):
- **Wildcard-роуты**: `/*` → `/*splat`. Пройтись по `src/routes/*.js` и
  `server.js` на предмет вайлдкардов в путях
- **`req.body`**: поведение по умолчанию изменилось (нет тела — `{}`,
  не `undefined`) — сверить с местами, где сейчас проверяется
  `if (!req.body)` или похожим паттерном
- **`res.redirect`**: сигнатура `res.redirect(url, status)` →
  `res.redirect(status, url)` — порядок аргументов поменялся местами,
  грепнуть все вызовы
- **`router.param`**: поведение с несколькими callback изменилось
- **`res.sendfile`** (нижний регистр) удалён — есть ли где-то такое
  написание (не `sendFile`)
- **`express-rate-limit`**: проверить в Stage 1.2, что версия,
  которую бампаем, заявлена совместимой с Express 5
- Это код, который **только что прошёл security review** (§6 старого
  квартального roadmap) — после апгрейда стоит точечно перепройти
  как минимум CSRF/cookies/rate-limit пункты того чек-листа, не весь
  список с нуля

3.5.1. Прочитать официальный Express 5 migration guide целиком, прежде чем трогать код
3.5.2. Апдейт зависимости, `npm test` — первая грубая проверка
3.5.3. Пройтись по списку рисков выше построчно (grep + чтение, не «наверное пронесёт»)
3.5.4. Правки по каждому найденному месту, с тестами после каждой правки, не пачкой
3.5.5. Ручной прогон auth-флоу целиком (логин/логаут/смена пароля/роли) — самое чувствительное место к поведенческим изменениям фреймворка
3.5.6. `npm run test:e2e` — обязательно перед тем как считать этап закрытым, не факультативно

## Stage 4 — Аутентификация: домашняя крипта → bcrypt

Решено в этом чате как низкий риск, «вечер работы» — тот же паттерн
миграции, что у вас уже есть для legacy SHA-256 → PBKDF2 (перехэшировать
при следующем успешном логине, не массовой миграцией БД).

4.1. `bcrypt` в зависимости
4.2. Новая функция хэширования в `src/auth/crypto.js`, старая (PBKDF2) остаётся для чтения legacy-хэшей
4.3. При логине: если хэш в старом формате — проверить им, при успехе перехэшировать в bcrypt и сохранить (тот же паттерн, что уже в проекте)
4.4. Тесты на оба пути (новый формат, legacy-миграция, неверный пароль не мигрирует — все три уже покрыты похожими тестами для предыдущей миграции, писать по аналогии)

## Stage 6 — God files на фронтенде (по мере повода, не отдельным проходом)

Не рефакторить ради рефакторинга (принцип квартала §18 остаётся в
силе даже вне квартального roadmap). Текущие размеры для ориентира:
`registry.js` 988 строк, `config.js` 720 строк.

Правило: трогаете конкретный кусок логики в одном из этих файлов по
другой причине (баг, фича) — заодно выносите этот кусок в отдельный
модуль. Не создавать отдельную задачу «разбить registry.js» без
повода.

Кандидаты на вынос, когда дойдёт очередь (нашли по ходу этой сессии):
- Аудит-панель заявки (рендер + `FIELD_LABELS`) из `registry.js`
- Построение фильтров (`org`/`supplier`/`month`/`counterparty`) из `registry.js`
