# Operations

Практическое руководство: запуск, обновление, бэкап, восстановление,
disaster recovery. Установка и базовый запуск подробно описаны в
[`README.md`](../README.md) — здесь эти шаги не дублируются, только
ссылка и то, чего в README нет: полная процедура обновления,
пошаговое восстановление и сценарий потери сервера.

## Запуск

Смотри `README.md`:
- [Quick start](../README.md#quick-start) — установка зависимостей и запуск для разработки (Windows/Linux/macOS)
- [Docker](../README.md#docker) — запуск в контейнере, переменные окружения, команды

Production без Docker — то же самое, что и dev-запуск (`node server.js`
или `npm start`, если есть скрипт в `package.json`); проект не требует
отдельной сборки (no build step), поэтому «development» и «production»
запуск технически не отличаются. Разница — в переменных окружения
(`NODE_ENV`, `PROCURE_TRUST_PROXY` при работе за reverse-proxy) и в том,
что порт 443/HTTPS обычно нужен «по-настоящему», а не с самоподписанным
сертификатом (см. `README.md` → Configuration).

## Обновление

1. **Backup.** Сначала бэкап, потом всё остальное — см. раздел ниже.
   Автобэкап (каждые 6 часов) не заменяет этот шаг: если обновление
   что-то сломает раньше следующего автобэкапа, откатываться будет не на
   что свежее.
2. **Обновление кода.** `git pull` (или разворачивание новой версии
   архива — смотря как вы деплоите).
3. **`npm ci`** (не `npm install`) — если менялись зависимости
   (`package-lock.json`). Для Docker это происходит автоматически при
   `docker compose up -d --build`.
4. **Миграции.** Ничего вручную запускать не нужно — `runMigrations()`
   (`src/db/schema.js`) выполняется автоматически при каждом старте
   сервера, идемпотентна (безопасно гонять повторно на уже
   смигрированной БД — это отдельно проверяется тестом
   `test/schema.test.js`).
5. **Запуск.** `node server.js` / `docker compose up -d --build` — см. README.
6. **Проверка.**
   - Сервер поднялся без ошибок в логе (`logs/access.log` +
     stdout/stderr процесса).
   - Открывается `https://<host>:<port>`, логин работает.
   - Версия в подвале/Конфиге (`О программе`) соответствует ожидаемой.
   - Если менялась схема БД — одна тестовая заявка создаётся и
     сохраняется без ошибок.
   - `docs/index.html` (встроенная документация) открывается по ссылке
     из интерфейса и не выдаёт 404.

## Backup

**Где лежит.** По умолчанию — `data/backups/` внутри проекта. Можно
указать другую папку (в т.ч. сетевую) в Конфиге → «Резервная копия» →
«Папка для автобэкапов» — тогда автобэкап и копии прикреплённых файлов
идут туда. Смысл: если сломается диск с рабочими данными, бэкап на нём
же не поможет.

**Автоматически:** каждые 6 часов (`BACKUP_INTERVAL_MS` в переменных
окружения, если нужно поменять интервал) создаётся:
- снапшот SQLite (`zakupki_<дата>_<время>.db`);
- зеркало прикреплённых файлов (`files_mirror/` — синхронизируется, не
  копируется каждый раз заново; `files_<снапшот>/` — точный слепок на
  момент этого конкретного бэкапа).

Снапшоты и их файловые папки старше **30 дней** удаляются автоматически
(age-based retention, не count-based — см. `src/services/backupService.js`).
`files_mirror/` не удаляется — это текущее зеркало, не история.

**Как создать вручную.** Конфиг → «Резервная копия»:
- «💾 Скачать JSON» — полный снапшот для восстановления: организации,
  настройки (включая данные поставщика по умолчанию), адреса доставки,
  шаблоны позиций, пользователи, заявки. **Это единственный формат,
  который принимает Restore** (см. ниже) — не `.db`.
- «🗄️ Скачать DB» — сырой файл SQLite, для техподдержки/ручного разбора,
  Restore его не принимает.

Через API (например, для внешнего скрипта или cron):
```bash
curl -sk -b cookies.txt https://<host>:<port>/api/backup -o backup.json
```
(нужна активная admin-сессия — см. `docs/index.html` → REST API).

**Как проверить, что бэкап рабочий.** Открыть скачанный JSON и убедиться,
что в нём реалистичное число `requests`/`orgs`/`users` (не 0, если в
системе реально есть данные) — сравнить с тем, что показывает
Конфиг → «О программе» на момент бэкапа. Формальный «restore drill»
(реально восстановиться из бэкапа на тестовом окружении и убедиться,
что приложение работает) roadmap выносит отдельным пунктом (§4.3) — этот
документ описывает механику, сам прогон drill'а — отдельная задача, не
делалась в рамках этого changeset.

## Restore

**Внимание: полностью заменяет текущие данные.** Возврата назад нет,
кроме как восстановиться из ДРУГОГО бэкапа (сделанного до этого).

1. Найти нужный JSON-бэкап (см. раздел Backup выше — свой или из
   `data/backups/`).
2. Конфиг → «Резервная копия» → «📂 Восстановить из JSON» → выбрать файл.
3. Приложение покажет модалку сравнения: сколько заявок/организаций/
   пользователей сейчас **против** того, что будет после восстановления
   — а также дату, когда сам файл бэкапа был сформирован (если она есть
   в файле). Проверить, что это действительно тот бэкап и та дата,
   которые нужны.
4. Подтвердить («Заменить всё»). Сервер:
   - заменяет все таблицы (`requests`, `orgs`, `users`, `addresses`,
     `templates`, настройки) содержимым бэкапа;
   - восстанавливает прикреплённые файлы (подписанные спецификации,
     счета, листы согласования) — сначала проверяет, нет ли их уже на
     диске, если нет — берёт из `files_mirror/` (зеркало бэкапов);
   - **инвалидирует все сессии** — все, кто был залогинен (включая вас),
     будут разлогинены. Это осознанное поведение, не баг: список
     пользователей после restore может быть другим, старые
     сессии/токены могут ссылаться на несуществующих больше
     пользователей.
5. Страница сама перезагрузится и покажет экран логина.

### Что проверять после восстановления

- Залогиниться под учёткой, которая должна существовать в
  восстановленных данных (не под той, что была до restore, если её
  больше нет).
- Число заявок/организаций/пользователей в Конфиге → «О программе»
  совпадает с тем, что показывала модалка подтверждения на шаге 3.
- Открыть 2-3 случайные заявки — позиции, суммы, статус на месте.
- Если ожидались прикреплённые файлы (подписанные спецификации/счета/
  листы согласования) — открыть хотя бы один такой файл и убедиться, что
  он реально скачивается, а не 404. Ответ `POST /api/restore` содержит
  `files.restored`/`files.missing` — если `missing > 0`, значит часть
  файлов не нашлась ни на диске, ни в `files_mirror/` (см. лог сервера,
  какие именно).
- Проверить Конфиг целиком (webhook'и, SMTP, сетевая папка) — эти поля
  входят в бэкап и тоже заменяются.

## Disaster Recovery

Сценарий «сервер потерян полностью» (сгорел диск, потеряна VM и т.п.):

```
Сервер потерян
   ↓
Развернуть окружение
   — новая машина/VM/контейнер, Node.js версии из package.json (engines),
     см. README → Requirements
   ↓
Получить проект
   — git clone / развернуть архив кода (без data/) — код сам по себе не
     содержит пользовательских данных
   ↓
Восстановить data
   — если бэкап хранился НЕ на той же машине (см. Backup выше, ровно
     ради этого сценария) — скопировать актуальный JSON-бэкап на новую
     машину
   ↓
Запустить
   — npm ci && node server.js (или docker compose up -d --build)
   — при первом запуске создастся новая, пустая БД и новый временный
     admin-пароль (см. лог первого запуска) — это ожидаемо, БД ещё
     пустая, потому что Restore — отдельный шаг, не часть запуска
   ↓
Восстановить (Restore)
   — залогиниться временным admin-паролем из лога → Конфиг → Restore
     из JSON-бэкапа (см. раздел Restore выше)
   ↓
Проверить
   — тот же чек-лист, что в разделе Restore → «Что проверять после
     восстановления» выше
```

Ключевой вывод из этого сценария: бэкап, лежащий **на той же машине**,
что и сама система (папка по умолчанию `data/backups/` внутри проекта),
не защищает от потери всей машины целиком. Если этот сценарий реален для
вашего окружения — настройте папку автобэкапов на отдельный
диск/сетевой ресурс (Конфиг → «Резервная копия», см. раздел Backup выше)
или синхронизируйте `data/backups/` во внешнее хранилище отдельным
механизмом (не входит в сам procure-it).
