# Security Review

**Дата последней проверки: 2026-09-20 (версия 26w36-b20)**

Этот документ — не описание новой security-системы, а срез существующей:
что уже сделано, где именно в коде, и что осознанно оставлено на потом.
Составлен по чек-листу `ROADMAP_Q4.md` §6.

Часть пунктов ниже закрыта не в рамках этого ревью, а серией из 7
итераций аудита незадолго до него (см. `CHANGELOG.md` 26w36-b15…b20) —
там же можно посмотреть, что именно было не так и как чинилось, если
интересна история, а не только текущее состояние.

| 2 | Secure cookie в production | ✅ | Там же — `secure: true` у обеих cookie (auth и csrf). Сервер всегда поднимается по HTTPS (см. `server.js`, self-signed сертификат генерируется автоматически при первом запуске), так что `secure: true` не блокирует обычную работу |

## Что нашли и починили по пути (26w36-b15…b20)

Не отдельно от этого ревью, а как раз тот материал, из которого оно во многом
и собрано. Полные описания — в `CHANGELOG.md`, здесь только список с точки
зрения security:

- Дубли username/email в `POST/PUT /api/users` не отклонялись — `run()`
  глотает нарушение UNIQUE и возвращает `false`, роуты возврат не
  проверяли. Пересоздание пользователя с тем же логином отвечало
  `{ok:true}`, ничего не меняя
- Сохранение страницы настроек стирало `smtpPass`/`networkPass` при
  КАЖДОМ сохранении (не только связанном с этими полями) — форма
  сознательно не подставляет пароль обратно, а `PUT /api/settings`
  безусловно перезаписывал пустой строкой
- `smtpPass` отдавался в `GET /api/settings` в открытом виде (`networkPass`
  уже маскировался, `smtpPass` — нет)
- Письмо сброса пароля: `href` без экранирования + `resetUrl` строился из
  сырого `req.headers.host` без валидации формата — при прямом доступе к
  серверу (без реверс-прокси) атакующий мог подделать `Host` в обычном
  HTTP-запросе и получить у приложения легитимное письмо для жертвы с
  фишинговой ссылкой
- Утечка сырого `e.message` клиенту в `/api/send-bitrix` и `/api/spec-docx`
- Несколько мест с orphan-файлами на диске при удалении организации/заявки
  (не security сама по себе, но накопление чувствительных PDF без владельца)
- `req.username` физически не выставлялся ни в одном защищённом роуте —
  функция, которая должна была это делать (`authMiddleware()`), нигде не
  подключена. Нашли при добавлении `audit_log.username` (26w36-b20) —
  до этого «кто сделал запрос» невозможно было узнать даже теоретически

## Известные ограничения (осознанно не в этом ревью)

- **users.email** — уникальность через частичный `UNIQUE INDEX`. На БД, где
  дубли email уже существовали ДО 26w36-b16, индекс не создастся (SQLite
  откажет), не блокируя запуск — но и не защищая. Нужно развести дубли
  вручную на таких БД (см. `src/db/schema.js`, комментарий у миграции)
- **`GET /api/audit?limit=`** — без верхней границы (`limit=-1` в SQLite
  означает «без лимита» вообще). Низкий риск: роут за `operatorOrAdmin`,
  но не bounded
- **Secrets в git history** — см. пункт 18 выше, требует реального репозитория
- Этот документ описывает код по состоянию на 26w36-b20. Следующее ревью
  имеет смысл делать не «через N месяцев по календарю», а при следующем
  значимом изменении security-поверхности (новый способ загрузки файлов,
  новый внешний webhook, смена auth-механизма) — раньше, если что-то из
  раздела «Известные ограничения» выше даст о себе знать на практике.

## Особое внимание (из ROADMAP_Q4.md)

Если при проверке git history (пункт 18) обнаружатся реальные секреты:

1. считать их скомпрометированными;
2. заменить (новый пароль/webhook/токен);
3. удалить из текущей конфигурации;
4. проверить логи доступа на предмет использования скомпрометированного
   секрета до его замены.

Переписывать git history (`git filter-repo`/`BFG`) само по себе не решает
проблему, если секрет уже мог утечь наружу (форк, локальные клоны,
CI-кэши) — сначала замена, потом уже, если нужно, чистка истории.
